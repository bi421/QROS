# Model Execution Boundary V1

**Status:** Proposed + implementation skeleton  
**Scope:** Research model execution only  
**Design principle:** provider-neutral, provenance-first, fail-closed

## 1. Goal

Provide one stable execution boundary for statistical, machine-learning, sequence,
or other research models without allowing any specific model implementation to
become part of the core research domain.

The boundary must let QROS:

- register executable adapters independently of model identity metadata;
- control model lifecycle explicitly;
- execute single and batch inference through one contract;
- preserve dataset identity and temporal scope at the inference boundary;
- return model output without fabricating confidence, accuracy, or evidence;
- fail closed when a model is missing or not ready.

## 2. Existing infrastructure that remains unchanged

The existing researchos.quant_engine.models.ModelRegistry remains the source of
truth for model identity, metadata, validation history, and contract
serialization.

The new runtime boundary does not replace that registry and does not add a
second identity system.

Responsibilities stay separated:

| Concern | Owner |
|---|---|
| Model identity / metadata | ModelContract + ModelRegistry |
| Executable implementation | ModelAdapter |
| Lifecycle of loaded adapters | ModelRuntime |
| Dataset truth | Dataset / DatasetVersion |
| Research execution | Experiment / Research Worker |
| Evaluation | Evaluation services |
| Calibration | Calibration services |
| Evidence certification | Evidence layer |

## 4. Runtime boundary

The executable boundary is:

    ModelAdapter
    ├── model_id
    ├── model_version
    ├── load()
    ├── unload()
    ├── is_ready()
    ├── predict(request)
    └── predict_batch(requests)

The runtime owns lifecycle coordination and dispatch only.

It does not:

- train models;
- select a trading action;
- silently substitute another model;
- silently repair invalid input;
- fabricate confidence or accuracy;
- write research evidence directly;
- mutate dataset truth.

## 5. Inference input contract

Every execution carries:

- dataset_hash;
- window_start;
- window_end;
- ordered input_schema;
- model-specific payload;
- explicit parameters;
- optional deterministic seed.

This makes the temporal and data boundary visible at the point where inference
occurs.

The runtime does not infer missing dataset identity.

## 6. Inference output contract

Every adapter returns:

- model_id;
- model_version;
- dataset_hash;
- raw model predictions;
- optional model-native metadata.

The runtime verifies that model identity and dataset identity match the request.

The runtime never converts a model-native score into a probability unless an
explicit calibration service performs that transformation.

## 7. Lifecycle policy

Lifecycle is explicit:

    register
      |
      +--> load
      |      |
      |      +--> ready
      |
      +--> unload

Calling predict on a non-ready adapter is an error.

Loading one adapter does not implicitly unload another adapter.

There is no process-global singleton.

Multiple ModelRuntime instances must be independently constructible for
workers, tests, and controlled experiments.

## 8. Batch policy

Batch inference is a performance boundary only.

Batch execution must preserve:

- request ordering;
- per-request dataset identity;
- per-request output identity;
- deterministic error attribution.

A batch result must not collapse distinct requests into one untraceable output.

## 9. Failure policy

The following are hard failures:

- unknown model id;
- duplicate adapter registration;
- prediction before readiness;
- adapter identity mismatch;
- model-version mismatch in the result;
- dataset-hash mismatch in the result;
- batch result count mismatch;
- adapter exception.

No fallback model is selected automatically.

No synthetic market data is generated by the runtime.

## 10. Provenance policy

The runtime is responsible only for preserving the declared execution boundary.

Higher layers remain responsible for:

- binding the execution to a ResearchRun;
- recording experiment configuration;
- attaching model contract identity;
- evaluating out-of-sample performance;
- calibrating uncertainty;
- creating evidence artifacts.

A runtime result without those bindings is an execution artifact, not a certified
research conclusion.

## 11. Security and isolation

The boundary must be safe to use from tenant-scoped workers.

The runtime itself remains stateless with respect to tenant identity.

Tenant authorization is owned by the application/service boundary.

Model adapters must not access unrelated tenant state or mutate shared research
repositories.

## 12. Implementation sequence

### Slice A — Contract

Implement:

- InferenceRequest;
- InferenceResult;
- ModelAdapter protocol;
- runtime error hierarchy.

### Slice B — Runtime

Implement:

- adapter registration;
- deterministic listing;
- explicit load/unload;
- readiness checks;
- single dispatch;
- batch dispatch;
- identity/result validation.

### Slice C — Conformance tests

Prove:

- duplicate/unknown handling;
- explicit lifecycle;
- no implicit fallback;
- deterministic ordering;
- independent runtimes;
- single/batch identity preservation;
- adapter errors propagate;
- result mismatch is rejected.

### Slice D — Provider adapters

Only after the boundary is green, implement concrete adapters behind it.

Each adapter must be added as a separate change with its own:

- dependency review;
- model artifact pin;
- input mapping;
- preprocessing contract;
- output mapping;
- evaluation plan;
- provenance evidence.

## 13. Non-goals for V1

This change intentionally does not implement:

- model training;
- model selection/ranking;
- auto-ML;
- probability calibration;
- online learning;
- live trading;
- tenant-facing model management UI;
- automatic model fallback.

## 14. Acceptance criteria

V1 is complete when:

1. the existing model registry remains backward compatible;
2. the runtime has no global singleton state;
3. inference cannot run before explicit readiness;
4. runtime output cannot claim a different model or dataset than requested;
5. batch ordering is preserved;
6. no fallback or synthetic-data behavior exists in the runtime;
7. conformance tests pass;
8. the architecture document and code express the same boundary.

## 15. Future extension

Future concrete adapters should be plug-in implementations behind this boundary.

The research system should remain organized around:

    real data
      -> explicit target
      -> temporal boundary
      -> baseline
      -> model execution
      -> OOS evaluation
      -> statistical validation
      -> calibration
      -> evidence

The model is a component of research, not the definition of research.
